## Interpretation

### What the data shows

**Weights 0-5 cluster tightly:** coalition-win rate 24-32%, mean coalition size 2.13-2.42, median turns 2.0, mostly iron-victory. The differences between weights 1, 3, 5 are within seed noise (n=50 → SE ≈ 7pp on a 24% rate).

**Weight=10 is a phase transition:** 96% coalition wins, 3.0 mean coalition size (≈ full 3-player set), median turns 1.0, ALL last-standing. The mechanism (verified by inspecting per-game records): every player allies with every other player on turn 1, leaving "exactly one non-eliminated coalition" — which the engine's `status()` declares the last-standing winner immediately. The coalition iron threshold is 10 + 4×3 = 22; total board iron is ~14, so iron-victory is unreachable for the all-allied coalition, but it doesn't need to be — being the only coalition wins by default. **This is an engine semantics finding worth flagging:** the "exactly one non-eliminated coalition" last-standing rule fires whether the other players were eliminated OR simply merged into the coalition. Sam should weigh whether the engine should distinguish.

**Why weight=0 still produces 32% coalition wins:** the alliance-aware candidate-generation in `samplePolicy` adds an `ally(T)` candidate with `typeValue = evaluate(post-apply-state)[player] + weight × controlIron(T)`. At weight=0 the bonus is zero, but `evaluate` doesn't track `basesInHand` (cost) or alliance arrays, so `evaluate(post-ally) ≈ evaluate(state)`. The ally candidate is therefore TIED with the `pass` candidate at the current state's score — and is picked whenever ALL build/attack candidates score LOWER than the current state (i.e., the move-set is "no good options"). So weight=0 isn't a true alliance-blind baseline; it's "ally as a do-nothing tie-breaker when other moves degrade position." A genuine alliance-blind baseline would set `alliancesEnabled=false`.

### Recommendation

**Keep `DEFAULT_POLICY_ALLIANCE_WEIGHT = 5`.** Reasoning:
- 5 is in the safe regime (no degenerate group-victory pattern).
- Within weights 0-5 the differences are noise — the heuristic can't strongly distinguish.
- Bumping to 10 produces gameplay-destroying everyone-allies-immediately behavior under the current `status()` semantics.
- The Phase 4 "alliance-aware leaf-evaluation" extension to `evaluate` (or a per-game alliance-event measurement) would be the right way to get more signal — Phase 3's heuristic-only sweep is too coarse.

### What this DOESN'T tell us

This sweep is heuristic-self-play. The strategic test — does an MCTS-aware agent using the alliance-aware candidate set find DEEPER alliance patterns the heuristic can't? — is Phase 5 work. The weights chosen here may matter more or less once MCTS is searching over alliance edges.
